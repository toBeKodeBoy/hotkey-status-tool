# 应用归属、趋势、冲突与菜单栏排名技术方案

日期：2026-11-08。状态：待实现；本次交付仅为方案，不代表功能或覆盖率已经达标。

## 目标与范围

实现前台应用归属、7/30 天 Swift Charts 趋势、多应用高频使用提醒、今日第一名实时显示。沿用 Swift 5、AppKit、CoreGraphics 与 macOS 14+，只在图表区域引入 SwiftUI，不引入第三方依赖。监听保持 listenOnly，事件原样返回，统计只存本机。

对应现有路线 v1.1 的应用维度及 v1.2 的趋势、冲突、菜单栏第一名；应用忽略名单作为冲突查询的基础配套。本任务不包含布局键名切换、导出或更新检查。完整版本仍需分别完成原功能清单中的其余事项。

## 当前实现与接入点

Models.swift 的 HotkeyRecord 只有组合键累计、今日与起止时间；StatsStore 使用 schema v2，按 combo 聚合，没有应用或日明细。EventTapMonitor 在主 RunLoop 过滤普通输入及自动重复后直接写入 Store。StatusBar 仅在展开菜单时读取累计 Top 5，setState 会清空按钮标题。main.swift 负责权限轮询和保存；Store 目前只有一个 onChange 回调，接入新消费者时不能覆盖窗口刷新。

## 事件与应用归属

新增可注入 FrontmostApplicationProviding，生产实现读取 NSWorkspace.shared.frontmostApplication，返回 bundle identifier 与 localizedName 的值快照。身份用 bundle identifier，不用显示名或 PID；取不到标识时归入独立 unknown 身份，显示“未知应用”，不按 PID 建永久统计。应用重命名只更新显示名，不拆分计数。

在已过滤的 keyDown 回调中立即读取快照及一次 now，再交给记录入口；不能延迟到异步 UI 刷新才读取前台应用。忽略名单命中后不计数、不输出快捷键日志。取不到应用仍计汇总。它表示采样时的前台上下文，不证明目标应用接收或执行了快捷键；快速切换存在系统采样竞态。

窗口应用明细显示“⌘T — 记录于 Safari”。累计 Top 5 来源显示累计贡献最多的应用，次数相同时按应用身份稳定排序；未知来源明确展示。不得采集窗口标题、文档路径或普通输入，也不在日志中输出应用名及应用统计。

## 存储与迁移

分两步交付 schema v3（应用累计）和 v4（日明细），最终客户端支持直接从 v1/v2/v3 升级至 v4。新增类型而不是立即改写现有数据：ApplicationIdentity、AppHotkeyRecord、DailyCount、StatisticsFile。组合键保持当前归一化策略，应用明细主键为 combo × app identity，日明细为该主键 × day。JSON 使用结构化记录数组，避免用字符串分隔符拼接主键。

v3 的应用累计记录必须保存 count、todayCount、todayDate、firstSeen、lastSeen，以及文件级统计时区 identifier；不能在 v3 阶段只保存累计后再指望 v4 恢复今日次数。v4 的应用累计记录保存 count、firstSeen、lastSeen；daily 保存按日次数。全局汇总由应用明细计算，避免两份累计值失配。兼容现有表格的 todayCount 从同一日明细查询生成。没有日期依据的累计保留在累计中，不伪造历史。

v1/v2 历史归为 unknown，累计与起止时间完整保留。旧文件没有统计时区，不能仅因 todayDate 格式合法就把它解释成新统计时区的日明细。原 todayDate/todayCount 作为 legacyToday 字段原样保留，并标明时区未知；不纳入 7/30 天图表、冲突和今日排名，界面说明“升级前日期统计因时区未知未纳入趋势”。如后续提供用户确认旧时区的流程，应单独设计，不自动猜测。v3 已保存统计时区，校验 todayDate 是该时区有效日期且 todayCount 在 0...count 内后，可将其作为该日的确定明细迁入 v4；无时区的预发布 v3 走 legacyToday 保护路径。v1 使用已有键码修正、过滤及合并规则，但先保留日期原值，不调用会按迁移当天归零的旧 migrate 实现，避免丢掉唯一尚存的日期信息。保留最早与最近时间，不声称恢复已混合键位。损坏、负数、重复明细或违反累计约束的数据拒绝迁移并显示存储错误，不静默修正。

迁移先读取并验证，再将原始字节写入同目录唯一备份；备份成功才构造目标并原子替换。未知版本、读取失败、解码失败或备份失败均阻止后续定时/退出写入。不存在的文件才视为空库；当前 load 的 try? 会混淆缺失与读取失败，需一并修正。迁移保存失败保留原文件和备份，内存数据及错误可见；重复启动不重复累加。

累计永久保留；日明细先保留所有自然日，满足既有“至少最近 30 个有记录的自然日”要求，未来裁剪另行设计。文件增长以聚合数据而非逐事件控制；性能验收覆盖大数据集。内存维护累计、今日及按日期/应用索引，每次有效事件只更新对应桶；7/30 天查询只读取窗口内的桶，避免实时排名在每次按键时扫描全部历史。

## 日期、趋势与冲突规则

注入 Clock、Calendar 和统计时区，生产使用公历及固定 yyyy-MM-dd 格式（不受系统地区与用户日历设置影响），默认首次创建文件或迁移时的本地时区并持久化其 identifier；之后系统时区改变不重分历史。应用界面标出统计时区。使用 Calendar 按自然日递增，不用 86400 秒跨日，覆盖夏令时。日志继续独立使用北京时间。

7/30 天窗口含今日，以统计时区的日界为界。图表输出固定 7/30 个有序日期点，缺失日显示 0；有升级前未分日累计时显示“历史累计不含完整日明细”，不能把零误称为确定未使用。支持全部应用或单应用、单组合键或当前筛选范围。今日/7 日/30 日/累计查询共享同一过滤规则。

TrendQuery 与 ConflictPolicy 为纯函数。冲突默认开启，默认阈值为每应用最近 7 个自然日达到 20 次，可在设置关闭或设为正整数。至少两个不同、未被忽略且身份已知的应用分别达到阈值才提醒；恰等于阈值也命中。未知应用不计入应用个数。结果附应用数、各应用次数和时间范围，文案为“多应用高频使用”，不判断系统快捷键抢占。阈值及忽略名单修改立即重算，忽略不删除历史。

## UI 与刷新

保留延迟创建的 AppKit 窗口，图表通过 NSHostingView 承载 SwiftUI Chart，包含 7/30 天切换、空状态、可访问文字描述。窗口关闭后复用，未创建时的数据更新仅更新快照。

新增统一的主线程变更分发，由 AppDelegate 串联 Store、窗口和菜单，避免单回调覆盖。今日第一名按今日次数降序、combo 字典序稳定破同分；零次不显示。运行中使用 imageLeading 显示图标与短名，长名按字符边界截断并在 tooltip 和可访问标签保留全名。仅第一名/状态/显示内容改变才修改按钮属性，菜单累计 Top 5 口径不变。

启动加载后、每次有效计数后、清空后、恢复监听后立即查询；午夜定时器、唤醒及系统时钟变化均重新计算并重新安排下一个日界，避免午夜没有输入时保留昨日冠军。暂停、无权限、监听失败隐藏排名，恢复后重新展示今日结果。Swift Charts 渲染可合并刷新，统计写入及排名不延迟到打开菜单。

## TDD 与 100% 覆盖率门禁

每个阶段先写可失败的行为检查并记录 Red，再实现 Green，最后重构后重复检查。测试使用临时目录、隔离偏好设置、假时钟、假应用提供器及可失败文件系统；不读写真实统计、日志、登录项或权限设置。

1. 应用采集：两应用 3+2 次汇总为 5，应用同名不同 ID、重命名、nil、忽略、普通输入、暂停及长按；验证不合格事件不调用应用采样与存储。
2. 存储：v1/v2/v3/v4 fixtures、原始备份字节一致、备份失败、读取与解码失败、未知版本、原子写失败、重复加载、清空、50 次保存及退出保存；校验累计/日期不变量和最早/最近时间；验证 v2→v3→v4 与 v2→v4 的累计、legacyToday 一致，带时区 v3 的今日明细完整保留，v1 过期日期不被归零，未知旧时区不被猜入趋势。
3. 日期查询：7/30 点、含今日边界、月底/年底、闰日、夏令时、固定统计时区、迁移前后切换时区、非公历系统设置、未来日期、历史缺失、应用/组合筛选、无数据及大数据量。
4. 冲突：0/1/2/多应用，阈值 -1/0/19/20/21、开关、忽略及 unknown、7 日边界、旧累计不参与，确保不改变记录。
5. 排名与生命周期：首次加载、同分、易主但未开菜单、清空、无输入跨日、睡眠唤醒、时钟改变、暂停恢复、无权限、长键名、未创建窗口、关闭重开、多消费者通知及无重复 UI 写入。
6. 桌面适配与图表：真实 NSWorkspace 取值、NSHostingView 创建/更新、图表切换与辅助功能、按钮标题及图标、定时器释放；用受控桌面测试覆盖自有适配代码，另做手工全局监听验收。

100% 要求为仓库自有 Swift 源码的行、函数、区域三项均覆盖，包含 UI、系统适配器及现有代码；不能仅声明新增策略模块达标。Apple 框架实现不属于分母。用 swiftc 的 profile-generate/profile-coverage-mapping 和 LLVM 工具合并所有测试进程覆盖率；将源码清单与报告逐项核对，漏报文件、零计数或 covered != count 均失败，不使用百分比四舍五入判定。不得为达标排除难测文件或删除错误分支。

现有 test-runtime.sh 与 test-logger.sh 仅对指定模块强制 100%，并非全项目证明。新增全源码覆盖脚本及受控桌面测试入口，逐步补齐现有缺口；若桌面环境或权限不可用，应明确报告未达全项目 100%，不能把手工验收计入 LLVM 覆盖率。覆盖率之外还需核对断言质量与边界结果。

## 实施与交付顺序

第一阶段为覆盖基线与测试注入点；第二阶段为应用身份和 v3 安全迁移；第三阶段为日明细、v4 迁移及查询；第四阶段为图表和冲突展示；第五阶段为菜单实时排名与全量验收。每阶段遵循 Red → Green → Refactor，并保持旧回归通过。数据模型修改在实现任务明确授权范围内进行，本次方案提交不触及存储。

实现完成后从根目录运行 ./prototype/test.sh、全源码覆盖检查及 ./prototype/build.sh。构建前检查已有进程，保持签名失败时旧包安全。桌面验收需先按键再开窗口、关闭重开、退出重启、两应用归属、跨日排名与权限撤销恢复；确认进程持续运行才报告启动成功。额外使用临时大数据文件检查每事件不扫描全部历史、图表不逐事件重建；记录实测耗时与机器环境，不预先声称性能达标。

功能分支使用 codex/ 前缀，按测试基础、应用迁移、趋势查询、界面排名拆分可审查提交；全部检查通过后推送。同步 prototype/README.md 的实际使用说明及设计/功能清单的实现状态。方案阶段只检查文档内容与引用，不运行产品构建，不宣称 TDD 或功能验收已经完成。
